# Questão 3 — Estratégia de testes para 1.000 req/s com P99 <= 30ms

## 1) Entendimento do problema
O serviço de agendamento recebe requisições para programar eventos que serão retomados no Kafka no horário definido.  
Como é parte crítica do produto, precisamos provar:
- **Throughput:** 1.000 req/s.
- **Latência:** P99 <= 30ms no endpoint de agendamento.
- **Resiliência:** comportamento correto sob falhas de Redis, worker e Kafka.

## 2) Premissas de validação
- Medição de latência no endpoint HTTP (server-side e client-side).
- Ambiente dedicado e estável.
- Dados de teste variados (pequeno/médio/grande).
- Resultado validado com repetição mínima de 3 execuções por cenário.

## 3) Testes que serão feitos
## 3.1 Funcionais e de integração
- **Unitários:** validação de payload, cálculo de horário, serialização.
- **Integração:** endpoint -> Redis/RQ -> worker -> publish Kafka.
- **Contrato:** formato do evento publicado no tópico Kafka.
- **Concorrência:** colisão de IDs, duplicidade, ordenação por horário.

## 3.2 Resiliência
- **Queda de serviços:** indisponibilidade de Redis/Kafka, timeout de rede.
- **Retomada de serviços:** retomada após falha e reconexão.
- **Idempotência:** evitar publicação duplicada em reentrega.
- **DLQ/caminho de erro:** eventos irrecuperáveis seguem trilha segura.

## 3.3 Performance
- **Carga:** rampa até 1.000 req/s, sustentação.
- **Estressar:** acima de 1.000 req/s para achar ponto de saturação.
- **Chamadas abruptas:** (ex.: 300 -> 1.200 req/s).
- **Testes longos:** 2h–8h para detectar degradação/memória.

## 4) Estratégia para comprovar meta de performance
Cenário principal:
1. Subida progressiva até 1.000 req/s em 5–10 min.
2. Estabilidade de 30 min.
3. Aprovação se:
   - P99 <= 30ms durante o período de estabilidade.
   - Taxa de erro <= 0,5%.
   - Sem crescimento contínuo de fila/backlog.

Cenários complementares:
- Com simulação de instabilidade de rede.

## 5) Ambiente e isolamento
- Instâncias dedicadas para API, Redis e Kafka.
- Mesma região/rede para reduzir viés de latência.
- CPU/memória dimensionadas de forma correta para suportar 1.000 req/s.
- Versões compatíveis e provisionadas de Python, Redis client, broker, sistema.

## 6) Ferramentas e execução
Ferramentas recomendadas:
- **k6** ou **Locust** (carga HTTP)
- **pytest + pytest-asyncio** (testes unitários e de integração)
- **Prometheus + Grafana** (métricas)
- **OpenTelemetry** (tracing)

Exemplo (k6):
```bash
k6 run --vus 300 --duration 30m scripts/scheduler_load.js
```

Exemplo (pytest):
```bash
pytest -m "unit or integration" -q
```

Pipeline CI/CD:
1. Step unitário + integração.
2. Step de performance curta.
3. Step noturno de carga.
4. Gate por threshold (P99, erro, backlog).

## 7) Métricas e critérios de aceite
Métricas obrigatórias:
- `http_req_duration` (p50/p95/p99)
- Requests por Segundo efetivo
- `% erros` (4xx/5xx)
- Uso de CPU/Memória
- Latência Redis/Kafka
- Lag de fila/consumer
- Taxa de duplicidade de evento

Critérios:
- **Aprovado:** 1.000 req/s sustentado + P99 <= 30ms + erro dentro do limite.
- **Reprovado:** qualquer violação persistente acima do definido.

## 8) Como garantir as premissas
- Repetir testes ao menos 3 vezes e usar mediana.
- Dados de teste e scripts auditados para reprodutibilidade.
- Comparar com dados históricos.
- Correlacionar métrica de app, infra e broker no mesmo intervalo.
- Registrar evidências (informações do dashboard durante a execução + relatório de execução).

## 9) Cuidados com falsos positivos/negativos
- **Falso positivo:** Incluir cenários com ruído controlado, não apenas o cenário ideal.  
  Mitigação: Simular falhas de rede, Redis e Kafka.
- **Falso negativo:** Gerar cargas artificiais que não refletem o uso real.
  Mitigação: Geradores de carga com comportamento realista.
- **Medição parcial:** Medição apenas da API.  
  Mitigação: Medir ponta a ponta com tracing.

## 10) Conclusão
A combinação de testes funcionais, resiliência e performance com gates objetivos comprova, com evidência técnica, se o scheduler atende 1.000 req/s e P99 <= 30ms de forma sustentada e operacionalmente segura.
